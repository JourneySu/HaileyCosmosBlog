# Internationalisation

This fork ships in one language, Traditional Chinese (`zh`), served at the
root (`/blog/`). The machinery below is still the original multi-language
architecture: `locales` in src/i18n/config.ts just happens to hold one entry
instead of several. Nothing was ripped out to get here, because a single
locale is simply the degenerate case of the same mechanism, and every page
that calls `getLocale`/`useTranslations`/`localizePath` needed zero changes
when the count went from two to one. See wiki/log.md, 2026-09-17, for the
removal of the second language and the optional back office that used to
live alongside it.

## The three decisions that shape everything else

**One page source, many outputs.** Every route lives under
`src/pages/[...locale]/`. The rest parameter is `undefined` for the default
language and the locale code for the others, so `about.astro` emits both
`/about/` and `/fr/about/`. There is no `src/pages/fr/` tree to keep in
sync, and no page to duplicate when a language is added. `localePaths()`
(src/i18n/index.ts) is the `getStaticPaths` of every static route:

```astro
import { localePaths } from "@i18n";
export const getStaticPaths = localePaths;
```

**The dictionary is a typed object, not string keys.** Components read
`t.reading.title`, never `t("reading.title")`. The first is autocompleted,
checked at build time and renamed by the editor's refactoring; the second is
a string nothing watches. `useTranslations(locale)` returns the whole
dictionary.

**A missing translation fails the build.** `src/i18n/ui/zh/` is written with
`as const`, and `Widen` (src/i18n/ui/types.ts) turns those literal types into
their base types while keeping the shape. Adding a second language would
require it to declare the exact same shape, so forgetting a key would be a
compile error and inventing one that does not exist in the reference
dictionary would be too. A partial translation that compiles is a partial
translation that reaches production.

## The pattern in a component

```astro
---
import { getLocale, localizePath, useTranslations } from "@i18n";

const locale = getLocale(Astro);
const t = useTranslations(locale);
---
<h2>{t.index.title}</h2>
<a href={localizePath("/blog/", locale)}>{t.nav.blog}</a>
```

`getLocale` reads `Astro.currentLocale`, which Astro derives from the URL
once the `i18n` block is configured (astro.config.mjs). It revalidates the
value with `isLocale` rather than trusting a URL segment to index a
dictionary.

Never write an internal path in a component. `localizePath` handles the
prefix, passes absolute URLs, `mailto:` and anchors straight through, and is
the only function the navigation calls. Route targets that a user may want
to redirect (`blog`, `topics`, `authors`, `about`, `contact`, `legal`) go
through `getSiteRoutes(locale)` in src/config/navData.json.ts.

## Content collections

Content is filed by language: `src/data/posts/zh/<slug>.md`. The glob loader
therefore produces prefixed ids (`zh/writing-html-that-ages-well`), which pays
off the moment a second language is added: filtering a language is a prefix
test, and two translations of one post would share a slug once the prefix is
removed, letting a language switcher point at the actual translation instead
of the home page. With one language configured, every id simply carries the
same `zh/` prefix.

src/i18n/content.ts owns every id manipulation:

- `entrySlug(id)` strips the prefix. **Any id used as a URL segment must go
  through it**, or URLs become `/blog/zh/my-post/`.
- `entryLocale(id)` returns the language.
- `getLocalizedCollection(collection, locale, filter?)` is the replacement
  for `getCollection`.
- `localesForEntry(collection, slug)` lists the languages a given entry
  actually exists in, so a hreflang is never declared toward a 404.

## The hreflang contract

`getAlternates(url, site, locale)` is the single source for both the
`<link rel="alternate" hreflang>` tags in BaseHead and, when more than one
language is configured, the language switcher in the navbar. They cannot
drift apart because they read the same function. `x-default` points at the
default language. The sitemap emits the same alternates because its
`serialize` hook (astro.config.mjs) re-reads the hreflang tags of the built
page in dist/, x-default included; the `i18n` option of `@astrojs/sitemap`
only pairs pages that carry none. Google cross-checks the two, and a
disagreement makes it ignore both. With one locale configured, every page
simply declares itself and `x-default` pointing at itself, which is valid and
harmless rather than broken.

RSS is per language: currently just `/rss.xml`. Adding a second language adds
its own feed at its own prefix, so a subscriber to one language is never sent
posts written in another.

`llms.txt` lists every configured language's URLs in one file per domain,
written in English, the working language of agents.

The 404 is the other exception. Most static hosts serve a single 404
whatever the requested URL, so it renders in the default language.

## Numbers and dates

`formatDate` and `formatNumber` go through `Intl` with the locale's `intl`
code (`zh-TW` here), so dates and thousand separators follow that locale's
conventions rather than being written by hand. Reading time, publication
dates and any count on a page all pass through these helpers.

## Adding a language

Three edits, no page touched:

1. Add the code to `locales` and its card to `localeMeta` in
   src/i18n/config.ts. `dir` is already part of the card, so a RTL language
   does not require reopening the layouts.
2. Create `src/i18n/ui/<code>/` by copying the `zh` slices. TypeScript
   refuses to compile until every key is present.
3. Add the content folders (`src/data/posts/<code>/` and so on).
4. Wire `<LocaleSwitcher />` back into Navbar.astro and Footer.astro (see
   below): it was removed from both when this fork dropped to one language,
   because a switcher with nothing to switch to is dead weight, not a feature.

The dictionary is split by domain (`chrome`, `index`, `pages`, `reading`)
rather than kept in one file, so one person can translate the reading slice
while another translates the index slice without touching the same file.

## The switcher

src/components/ui/locale-switcher/LocaleSwitcher.astro still exists and still
changes shape with the number of languages (a segmented control for two, a
dropdown from three), but this fork calls it from nowhere: Navbar.astro and
Footer.astro dropped their `<LocaleSwitcher />` calls when `locales` shrank to
one, on 2026-09-17. It is the one component in this theme kept deliberately
unused rather than deleted, exactly like the other now-uncalled sections
(WritersStrip, NewsletterInvite): reintroducing a language is a matter of
calling it again, not rebuilding it. No flags: a flag names a country, not a
language. Links carry `data-astro-reload` because the target document has a
different `lang`, `dir` and hreflang set, and the client router only swaps
the body.
